# Route B — Internal Router via decision-only LoRA SFT

Status: implementation started 2026-10-30. Deadline 2026-11-16.

## 1. Question

Under one average output-token budget `B`, does a model that decides its own
Thinking / NoThinking mode beat fixed modes, a budget-matched random router, and a
frozen-model external router?

This is route B of the group split: the decision lives **inside** the model
(LoRA), not in a separate classifier over frozen features (route A, teammate).

## 2. Why SFT and not a reproduction of the paper's RL

AdaptThink trains with RL on 8xH800 for 32 h. On one V100-32GB (no bf16, no
FlashAttention-2) the equivalent job is O(1,500-2,500) V100-hours against a
budget of roughly 100-150 V100-hours, and the verl path in this fork assumes a
multi-GPU FSDP setup. A 5%-scale RL run is likely to learn nothing and to consume
the week that is needed for evaluation and writing.

More importantly, the interesting claim is testable without full RL:

> When the answer generator is frozen, routing is a two-armed bandit per problem.
> The optimal policy is `NoThinking if R_NT(x) >= R_T(x)`, which supervised
> distillation can learn directly. AdaptThink's RL gain must therefore come from
> the *generation* policy co-adapting, not from the routing decision alone.

We test this with three cheap arms: decision-only SFT (frozen generation),
decision + NoThinking-solution SFT (generation co-adapts), and a single-step
policy-gradient variant that optimises the paper's constrained advantage
`1(NoThinking)*delta + R(x,y) - R_ref(x)` over cached rewards.

## 3. Method: the first token is the router

The first generated token decides the mode: `</think>` (id 151649) starts a
NoThinking answer, anything else starts Thinking. Define

    p_NT(x) = P(y_1 = </think> | x) under the LoRA model.

Training loss (decision only, no response tokens touched):

    L = -[ y * log p_NT + (1 - y) * log(1 - p_NT) ]

so the solver's behaviour is unchanged and the ablation "routing gain vs solving
ability change" required by the group notes stays clean.

Budget knob: route NoThinking iff `p_NT(x) >= t`. Sweeping `t` traces the same
Accuracy-Token frontier the external router traces with its score threshold, so
the two routes are directly comparable. This also removes the route-B weakness
noted in the design doc ("cannot reliably control the budget"): the budget is
controlled by a threshold, not by hoping the policy's mode probability is
calibrated.

Router cost to report separately: one 1.5B forward pass per problem
(prompt <= 1024 tokens), no decoding.

## 4. Data

| Piece | Source | Cost |
| --- | --- | --- |
| Thinking correctness per problem (K >= 16) | `data/train/ref_results/...1.5B...K16.json`, released by the AdaptThink authors, byte-identical to upstream THU-KEG | 0 GPU |
| NoThinking correctness per problem (K = 4) | generated by us on a stratified 3,000-problem subset of DeepScaleR | ~6-8 V100 h |
| Training manifest | `data/splits/sft_train_3000_seed42.json` | 0 GPU |

Manifest properties (all verified by `scripts/make_sft_manifest.py`):

- DeepScaleR deduplicated 40,315 -> 39,135 unique problems (1,180 duplicate rows).
- Leakage removal runs in two layers, because exact matching is not enough:
  - exact: 3 problems whose whitespace-free lowercase text equals a test/val
    question (1 test, 2 validation); 1 problem has no reference row.
  - near-duplicate: 27 more removed at character 8-gram similarity >= 0.80
    (max of Jaccard and containment). This layer is not cosmetic - it caught
    `deepscaler:6417` vs `math:489`, the *same* problem and same answer 15 whose
    only difference is whether a comma sits inside the `$...$` (similarity 0.818).
    Whitespace normalisation cannot see that.
- Audit after regeneration (`scripts/check_split_quality.py`): worst similarity to
  any held-out question is 0.667; 0 pairs at >= 0.70. The 18 pairs above 0.50 are
  template twins that share MATH boilerplate ("express your answer in interval
  notation") but are different questions, printed in the audit for review.
- 5 strata by reference Thinking accuracy, 600 problems each: never 0, rare
  (0,0.25], sometimes (0.25,0.5], usually (0.5,0.875], always (0.875,1].
- Round-robin ordering, so the 600-problem pilot is a strict stratified subset of
  the 3,000 run: calibration GPU time is never wasted.
- Expected label mix at `acc_thinking >= 0.5`: 1,345 NoThinking / 1,655 Thinking.

## 5. Evaluation protocol

- Test: the canonical split (GSM8K 330 / MATH-500 125 / AIME 30x16), untouched.
- Validation: `data/splits/adaptthink_val_seed142.json` (GSM8K 300 + MATH-500 150
  drawn from the rows the test split did not use; seeds 142 / 200142 instead of
  42 / 200042). Thresholds are chosen on validation only.
- AIME 2024 has no validation rows (all 30 are test), so its threshold is
  transferred and AIME is reported as its own panel, never tuned.
- Scoring uses `src/adapt_think_rm.py` only. Budget matching compares actual
  measured tokens, not requested ones.
- Two evaluation modes: (a) replay - the LoRA only supplies `p_NT`, generation
  comes from the cached frozen-model outputs, zero extra GPU, isolates routing
  quality; (b) self-generation with the LoRA weights, which is the deployment
  number and costs one extra Slurm run.

## 8. Risks

1. NoThinking truncation on hard DeepScaleR problems inflates generation cost and
   biases labels toward "NoThinking fails". Mitigation: 8,192-token cap for labels
   (documented deviation from the 16,384 evaluation cap), truncation recorded per row.
2. A one-token decision may be too weak a control surface (LoRA may not move
   `p_NT` enough). Mitigation: check the `p_NT` distribution shift on a held-out
   slice before running the full curve; fall back to response-level SFT (arm 2).
3. AIME's 30 questions x 16 draws remain noisy and 47.7% of Thinking generations
   truncate at 16,384: report AIME with explicit error bars and truncation rates,
   never as the headline claim.

## 9. Compute environments

Two clusters are available and they are **not interchangeable for the final numbers**.

| | NTU TC1 (V100-32GB) | Lab cluster (H200) |
| --- | --- | --- |
| Scheduler | Slurm (`sbatch`) | PBS (`qsub`), `-P ds_ccds_wei.lu -q gpu_ded` |
| Concurrency cap | 1 GPU | 2 GPUs per user, 48 h per job |
| Precision | fp16 only (no bf16, no FlashAttention-2) | bf16 + FlashAttention |
| Launcher | `scripts/ntu_nothinking_train.sbatch` | `scripts/lab_nothinking_train.pbs` |

Rule: **labels and the final test-set evaluation should be produced in the same
environment.** The router label only needs a correctness estimate, so generating
it on H200 is fine, but the reported accuracy must not mix a bf16-generated
NoThinking set with an fp16-evaluated one. Deciding now: if the lab cluster is
available, run both the label generation and the final evaluation there, and use
TC1 only as the fallback.

The PBS script splits the work into `SHARDS` independent single-GPU processes
instead of one tensor-parallel job: the requests are independent, so tensor
parallelism would add communication cost for no benefit. Two shards fit exactly
inside the 2-GPU cap.
